# Локальные данные и восстановление

Описание текущего формата и проверок от 27 октября 2026 года. Общие модули: `shared/state-codec.js`, `shared/state-journal.js`. Слой файлов Windows: `desktop/state-store.cjs`.

## Где находятся данные

- Windows: профильная версия сохраняет прежний `app.getPath('userData')`, обычно `%APPDATA%/Focus Break`; точный путь показан в настройках. Новый Portable выбирает `Focus Break Data` рядом с внешним EXE. Служебные данные Chromium тоже перенаправляются туда до ready. Абсолютная переменная `FOCUS_BREAK_DATA_DIR` имеет приоритет для явно выбранного / тестового каталога. Подробности и переход со старых кандидатов: [PORTABLE.md](PORTABLE.md).
- Android: Capacitor Preferences. Работу на устройстве ещё предстоит проверить.
- Браузер: localStorage конкретного origin. Это отдельное хранилище, браузерные данные не являются копией Windows-файла.

Основной источник истины — один журнал платформы. Renderer Electron обращается к нему через фиксированные IPC, без прямого доступа к файловой системе. Основной сценарий не отправляет данные в сеть.

## Открытый JSON-формат

Ручной экспорт — JSON UTF-8 с полем `version: 2`. Импорт также принимает старый `version: 1` и внутренний формат журнала. Максимальный размер импортируемого файла и внутреннего документа — 5 000 000 байт UTF-8. При превышении операция отклоняется целиком, существующие данные сохраняются. Экспорт компактный, чтобы добавленные пробелы не делали копию слишком большой для обратного импорта.

| Поле | Содержимое |
| --- | --- |
| `version` | 1 или 2; другие версии открывают режим восстановления без автосохранения |
| `settings` | Объект; длительности `focus` 1–120, `short` 1–30, `long` 1–60 минут, `goal` 1–12; язык `ru`/`en`; булевы настройки |
| `tasks` | Массив задач с непустыми уникальными строковыми `id` и `text` |
| Поля задачи | `completedAt` — timestamp в миллисекундах или null; `project` — строка; `tags` — массив строк; `priority` — low/normal/high; `dueDate` — YYYY-MM-DD или пустая строка; `repeat` — none/daily/weekdays/weekly; `estimate` — целое 1–20; `seriesId` — идентификатор серии |
| `history` | Массив сессий с уникальными строковыми `id`, корректным `endedAt`, целым `seconds` 1–7200; необязательными `task`, `project`, `tags` |
| `completedTasks` | Необязательный массив счётчиков выполненных задач: уникальные `id`, `completedAt` |
| `notes` | Необязательный объект: ключ YYYY-MM-DD, значение — полный текст заметки |
| `trash` | Необязательный массив `{ task: <полный снимок задачи>, deletedAt: <timestamp в мс> }`; ID задач уникальны одновременно среди рабочих задач и корзины |
| `activeTask`, `cycle`, `updatedAt` | Выбранная задача, счётчик цикла, время изменения состояния |
| `timer` | Необязательное состояние таймера: mode, running, started, remaining, total, endAt, taskSnapshot |

Даты проверяются по календарю, включая число дней месяца. Таймер принимает только известный режим, булевы флаги и допустимые длительности. Неизвестные поля задач, сессий, настроек и корневого состояния сохраняются при загрузке. Их наличие не означает, что UI поддерживает соответствующую функцию.

Внешние данные сначала полностью проходят `decodeDocument`/`validateState`, затем `restoreState`. Неверные записи не удаляются незаметно: отклоняется весь документ. `StateError.details` содержит пути полей с ошибками; UI сейчас показывает причину общего уровня. Детального отчёта по полям в UI ещё нет.

При миграции v1 → v2 сохраняются идентификаторы и все записи. Отсутствующие новые поля получают значения по умолчанию. Если `completedTasks` отсутствует, счётчики восстанавливаются из завершённых задач. Импорт никогда не запускает таймер из копии автоматически. Отдельный предел количества задач, сессий и дней заметок при загрузке удалён; ограничение общего размера остаётся.

Корзина — добавочное поле v2. Старые копии без `trash` получают пустую корзину. Удаление и очистка выполненных перемещают в неё полный снимок задачи. Восстановление сохраняет ID, завершённость, повтор, проект, теги и дополнительные поля; статистика и история сессий не меняются. Рабочий таймер сохраняет свой снимок удалённой задачи. Повторное завершение исходной задачи не создаёт экземпляр, уже находящийся в корзине. При конфликте ID пакетное восстановление останавливается до изменения коллекций.

Корзина сохраняется в основном журнале, автоматических копиях и ручном JSON-экспорте. Автоматической очистки по сроку нет; содержимое учитывается в лимите 5 МБ. UI поддерживает поиск, восстановление одной / всех задач и кратковременную отмену удаления. Окончательное удаление из корзины ещё не реализовано. Этот механизм не является готовым протоколом синхронизации устройств.

Старые установщики не понимают новую оболочку журнала. Не открывайте обновлённое хранилище старой сборкой: перед откатом экспортируйте данные и сохраните каталог userData отдельно. Поддержка чтения старых копий новой версией не означает, что старый код может безопасно записывать новый формат.

## Внутренний журнал

Пример оболочки:

```json
{
  "format": "focus-break-journal",
  "storageVersion": 1,
  "sequence": 1,
  "checksum": "8-символьная CRC32",
  "payload": { "version": 2, "settings": {}, "tasks": [], "history": [] }
}
```

`checksum` вычисляется как CRC32 от UTF-8 `JSON.stringify(payload)`. Она обнаруживает случайные изменения; это не шифрование, подпись или защита от намеренной подмены. `sequence` — номер локальной записи журнала, а не версия записи для синхронизации устройств.

| Назначение | Windows | Браузер / Preferences |
| --- | --- | --- |
| Основное состояние | `focus-break.json` | `focus-break:v1` |
| Предыдущее исправное | `focus-break.last-good.json` | `focus-break:v1:last-good` |
| Незавершённая запись | `focus-break.pending.json` | `focus-break:v1:pending` |
| Аварийный черновик браузера | Не используется renderer | `focus-break:v1:draft` |
| Контрольные копии | `backups/*.json` | Ключи `focus-break:v1:checkpoint:*` |

Сохранения выполняются последовательно: проверка данных → проверка неизменности основного снимка → pending → предыдущий исправный снимок → основной файл. Windows записывает каждый снимок в уникальный временный файл с `fsync` и `rename`. При миграции, импорте, сбросе и восстановлении старые данные сначала сохраняются отдельно; ошибка создания такой копии останавливает замену. Windows-копия сохраняет исходные байты даже при неверном UTF-8.

Браузер синхронно записывает черновик перед асинхронным сохранением. В поддерживающих Web Locks браузерах операции разных вкладок сериализуются. Изменение основного состояния другим окном вызывает конфликт вместо молчаливой перезаписи. Это не многопользовательская синхронизация; при конфликте нужно экспортировать собственные изменения перед дальнейшими действиями.

## Как восстановить

1. При повреждении, неизвестной версии или незавершённой записи приложение приостанавливает автосохранение и показывает диалог.
2. Сначала скачайте исходные данные. После ошибки сохранения экспорт содержит текущее состояние в памяти с последними изменениями.
3. Восстановите предложенную исправную копию / черновик либо выберите собственный JSON-файл. Предыдущее содержимое сохраняется отдельно до замены.
4. Если нет доступа к диску или он заполнен, освободите место / восстановите доступ и повторите проверку. Не удаляйте единственный исходный файл.

Сброс рабочих данных сохраняет локальную контрольную копию и прямо предупреждает об этом. Это не полное удаление персональных данных. UI управления контрольными копиями и полного удаления ещё не реализован. В Windows файлы из `backups` можно импортировать вручную; у браузерных и Android-копий пока нет отдельного списка в UI. Автоматического удаления старых контрольных копий пока нет.

Закрытие Electron запрашивает у renderer завершение сохранения и ждёт очередь записей. Если подтверждения нет, приложение предлагает остаться и экспортировать данные. Это не заменяет резервную копию на другом носителе и не гарантирует сохранность при отказе самого накопителя. Принудительное завершение и Android lifecycle требуют дальнейшей нативной приёмки.

Этот handshake относится к обычному выходу через `app.quit`. В Windows [событие before-quit не вызывается при завершении работы / перезапуске системы и выходе из учётной записи](https://www.electronjs.org/docs/latest/api/app#event-before-quit). Состояние записывается на каждое действие, незавершённая файловая запись может восстанавливаться из pending; отдельная проверка последних изменений при shutdown/logoff остаётся обязательным release gate.

## Проверки

`npm test` проверяет валидацию, миграции, размеры, Unicode, очереди, контрольные копии, конфликт, отказ на каждом шаге записи, сценарий прерванного сохранения и реальный файловый адаптер Windows в изолированном каталоге. `npm run test:e2e` проверяет диалог восстановления, офлайн-восстановление, импорт, отказ browser storage, перезагрузку и доступность.

Процесс Electron в текущей среде не удалось запустить из-за ACL sandbox. Нативное завершение приложения, отключение питания, установка и обновление не проверены. APK не собран. Юнит-тест файлового адаптера и browser-тесты не заменяют эти проверки.
